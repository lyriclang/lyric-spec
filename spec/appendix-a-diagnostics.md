# Appendix A — Diagnostic catalogue

> **Generated** from the toolchain's `diagnostics.toml` by `tooling/diagnostics/appendix.py`; not edited by hand.
> Source of the decisions: [11 Tooling and interop G9](https://github.com/lyriclang/lyric/blob/main/design/v5/spec/11-werkzeuge-interop.md).

Every code the reference toolchain reports, with its severity, the chapter whose rule it is, and when it is
reported. The **code and the severity are contract**; the message's wording is not (16 §1). `lyric explain CODE`
prints a code's whole entry: its explanation, a program that reports it and the program put right. A retired
code is no longer reported, and its number is not given again.

Severities: **E** error, **W** warning, **H** hint, **P** panic (at run time, exit code 101).

| LYR-RT0017 | P | [06-errors](06-errors.md) | control reached code the compiler holds unreachable | Control arrived where the compiler knows it cannot arrive — behind a call that does not return, behind a match that covers every case. That is a bug in the compiler: the debug profile panics with this code; the release profile stops with the processor's trap, which the runtime reports as a crash. Report it with the program. |
| LYR-RT0018 | P | [10-concurrency](10-concurrency.md) | a deadlock | Every task of a thread waits — for a channel, a lock, another task — and nothing can wake one: no task is ready, none sleeps, no other thread lives. The wait panics in the waiting task. |
| LYR-RT0019 | P | [10-concurrency](10-concurrency.md) | a lock poisoned by a panic | A task acquires a `Mutex`, `RwLock` or `Once` whose holder panicked while it held it. The scheduler released the lock and poisoned it; the panic names the first panic's code and message. |
| LYR-RT0020 | P | [16-diagnostics](16-diagnostics.md) | the runtime found its own invariant broken | The runtime met a state its own rules exclude — a thread allocating that the collector does not know, an object whose descriptor gives no size, a pointer the collector's map of a type does not name, a young object stored without its barrier, a coroutine whose descriptor is no coroutine's. That is a bug in the runtime or in the compiler, never in the program. |
| LYR-RT0021 | P | [13-abi](13-abi.md) | an integer from C that no variant of the enum stands for | A C function declared to return a `@Layout` enum returned an integer that is none of the enum's variants. A C enum may hold any integer of its type; a Lyric enum holds one of its variants, the first as 0, the next as 1, in the order they are written. |
| LYR-RT0022 | P | [13-abi](13-abi.md) | a Lyric function called from a thread Lyric does not run | C called a Lyric function through its pointer on a thread the runtime does not know: one C started itself, which no collector attached. A Callback that returns nothing goes to the thread that made it; any other call — a function's, a Callback's that returns a value, one whose thread runs no scheduler — has no Lyric to run on, and the process ends. An export called before `lyr_init` started the runtime ends it the same way. |
| LYR-RT0023 | P | [13-abi](13-abi.md) | a GcHandle that holds another class's object | A GcHandle made again from C's pointer with `GcHandle<T>.from` was read, and the object its root holds is of another class than `T`, or the root holds none. |
